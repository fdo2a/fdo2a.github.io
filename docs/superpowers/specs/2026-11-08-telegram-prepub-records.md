# 텔레그램이 발행 전 기록을 읽는다 — 2단계 (2026-11-08)

## 왜

1단계(`2026-11-08-prepub-record.md`)는 US·KR 일간 발행 커밋에 `verification/<m>/<D>.json` 을 남긴다. 그 기록을 사용자가
보지 못하면 「검증 장치가 있다」는 말은 증명되지 않는다. 사용자 결정(11/08): A안 — 발행 건별 알림(5분) + 기존 09시 매일 요약.
루틴·게이트·기록 형식은 바꾸지 않는다. 텔레그램 토큰은 맥 키체인만(클라우드에서 보내지 않는다). 대시보드·새 검사 없음.

## 구성

| 파일 | 몫 |
|---|---|
| `scripts/verification/repo_check.py` | 맥이 직접 하는 짝 확인. 루틴의 `record.verify` 와 **다른 함수**(루틴 경로 무변경) |
| `scripts/review/prepub_view.py` | 글 하나의 상태 계산·문장 — 발행 건별 알림과 매일 요약이 함께 쓴다 |
| `scripts/review/publish_watch.py` | 5분 회차의 판단: 기준점·사건·미발행·전송 |
| `scripts/verify_publish.py` | 진입점. 2.5단계부터 GitHub Actions(`--github`), 상태는 `alerts-state` 브랜치 — 아래 「2.5단계」 절 |

매일 요약(`verify_digest.py`)과 **상태 파일·실행 경로·전송 이력이 따로**다. 요약은 발행 상태를 읽기만 한다(꼬리 줄).

## 두 사실을 따로 낸다

- **[맥이 직접 확인]** 범주마다 일치/불일치/대조 불가: 글 지문, 검사기 목록(**기록 커밋의 설정** 기준 — 지금 설정과 비교하면
  검사기가 늘 때마다 과거 기록이 불일치가 된다), 검사 코드, 레포 안 코드·원장 다이제스트, 레포 보존 입력(`repo:`),
  작업 공간 전용 입력(항상 대조 불가). 불일치가 하나라도 있으면 「불일치」, 대조 불가가 있으면 「일부 확인」 — **「일치」라고 하지 않는다.**
- **[루틴이 남긴 검사 결과]** 기록 그대로: 판정·발행 가능·검증 완료·필수 통과 수·막은 것·판정 불가·실행 안 함·일부만·노트 수치·
  참고 실패·경고·숫자 대조 수. 요약 필드가 없으면 「통과」로 보지 않는다.
- 맥은 짝만 다시 본다. 검사가 실제로 돌았다는 것은 루틴의 자기 기록에 기댄다. 같은 데이터·같은 검사 논리라 원자료 자체의
  오류는 발행 전·후 모두 놓친다 — 「두 겹 검증」이라고 하지 않는다.

## 기준 판과 정정

- 기준 = 그 날짜 **기록 파일을 처음 담은 커밋**. 「처음 공개된 판」이라 부르지 않는다(git 그래프는 공개 시점을 증명하지 못한다).
  글을 추가한 커밋과 다르면 그렇게 적는다. 글·기록을 추가한 커밋이 2개 이상(지웠다 다시 추가)이면 판정 불가.
- 그 뒤 판은 짝 경보를 만들지 않는다. 이웃 판끼리 `review.prose.typography`(root 없이): True 조판, False **조판 외 변경**
  (본문 정정이라 단정하지 않는다), None·merge·삭제 = 판정 불가. 정정은 발행 건별 알림을 만들지 않고 요약에만.

## 5분 회차

- 기준점은 **마지막으로 정상 확인한 원격 커밋**(`last_seen`) — 시간이 아니다. `last_seen..tip` 에서 바뀐 대상만 다시 계산.
  기준점이 지금 이력의 조상이 아니면 「그 사이를 다 봤다고 할 수 없다」 알리고 전부 다시 계산.
- 조회(fetch·읽기) 실패: 기준점을 옮기지 않고 미발행 판정도 하지 않는다. 마지막 정상 확인 2시간 뒤 한 번 알리고, 복구되면 알린다.
- 미발행: `routine_due.us_session/kr_session` + **그 커밋의** 휴장 달력. 기준 시각 US 세션 D → D+1 12:00 KST(금요일 → 토요일),
  KR D → D 23:00 KST. 「원인: 확인 불가」 — 「보류」라 단정하지 않는다. 경보 뒤 글이 오면 「미발행 해소」. 미해소 세션은 기한 없이 보존.
  달력을 못 읽으면 그 시장의 판정을 멈춘다(빈 달력 = 휴일을 거래일로 보는 거짓 경보). 달력에 없는 휴장일은 여전히 거짓 경보.
- 사건 식별자는 내용에서 정해진다(같은 사건 = 같은 식별자). 저장 → 전송 → 저장. 보낸 뒤 저장이 실패하면 다시 보낸다 —
  **로컬 상태가 보존되고 Git 이력에 접근할 수 있는 한 미전송 사건을 재시도하며, 중복 전송을 허용한다**(맥 디스크·상태 파일이 망가지거나 이력을 못 읽으면 보장하지 않는다). 전송 실패는 pending 으로 남겨 같은 식별자로
  재시도(순서 유지). 사건 추가와 기준점 갱신은 **한 번의 원자적 저장**이라, 그 사이에 꺼져도 기준점만 앞서 가지 않는다.
- 미발행 해소는 경고를 **실제로 보낸 뒤**에만. 경고가 아직 대기 중이면 취소하고 「늦은 발행」, 경고 없이 기준 시각 뒤에 처음 봤으면
  커밋 시각으로 늦었는지만 추정해 「늦은 발행」(경고가 있었다고 하지 않는다).
- 상태 파일 손상 → 따로 옮기고 새로 시작, 적용일 이후 전부 다시 계산(이미 받은 알림이 다시 올 수 있다고 알린다).
- 5분은 맥이 깨어 있고 네트워크가 될 때의 목표. 런처(`runner_launch.py`, 검토 러너와 공용)는 바꾸지 않았다 — 런처·맥·텔레그램이
  함께 죽으면 실시간 알림은 없고, 매일 요약이 「마지막 정상 확인 n시간 전」으로 늦게 알린다.

## 세션 상태와 글 사라짐(codex 구현 검토 4회 반영)

| 세션 상태 | 뜻 | 글이 올라오면 |
|---|---|---|
| (없음) | 기준 시각 전 | 기준 시각 뒤 처음 보면 커밋 시각으로 `ok`/`late` |
| `missing` | 미발행 경고를 만들었다 | 경고를 보내려 한 적 있으면 재전송 뒤 「해소」, 한 번도 안 보냈으면 취소 + 「늦은 발행」 |
| `missing_quiet` | 첫 실행 기준선에서 경고 없이 잡음 | 「늦은 발행」(받은 적 없는 경고의 해소를 보내지 않는다) |
| `gone` | 올라갔던 글이 지금 없다 | `ok` + 글 쪽 「다시 올라옴」 |
| `ok`·`late`·`resolved` | 끝 | 지워지면 `gone`(이미 `missing*` 이면 덮지 않는다) |

- 사이 커밋은 `git log -m --no-renames` 로 따라간다 — merge 안에서만 생긴 글, 옮긴 글의 옛 경로도 잡는다. 맥이 보기 전에
  올라왔다 사라진 글도 「사라짐」.
- 첫 실행은 기준선: `clean()`(같은 커밋·짝 일치(작업 공간 입력만 대조 불가)·발행 가능·검증 완료·판정 `pass`)이 아닌 글만 알린다.
- 전송 전 `attempted` 를 저장한다 — 보내려 한 뒤로는 텔레그램이 받았을 수 있다. 저장을 못 하면 보내지 않는다.
- git 읽기 오류는 대조 불가로 굳히지 않고 회차를 멈춘다(기준점 그대로). 계속되면 2시간 뒤 조회 실패 알림.
- 매일 요약은 2단계 모듈을 쓸 때 불러오고 어떤 예외도 격리한다 — 2단계가 고장 나도 09시 요약은 나간다.

## 2.5단계 — 계산은 GitHub, 전송은 Cloudflare (2026-11-10)

원칙(사용자 결정): **AI 가 고칠 수 있는 코드에는 텔레그램 토큰을 주지 않는다.** 그래서 위 「5분 회차」의 맥 실행·맥 전송은 없어졌다.
위 절들의 판단 규칙(기준점·미발행·사라짐·기준선)은 그대로이고, 아래만 바뀐다. 형식의 정본은 레포 밖 계약 문서
`alerts-contract-2.5.md`(프로젝트 루트), 설계는 같은 자리의 `design-2.5-github-cloudflare.md`(뒤 판이 우선).

| 자리 | 몫 |
|---|---|
| `.github/workflows/publish-watch.yml` | 발행 push(`posts/**`·`kr/posts/**`·`verification/**`) + 기준 시각 맞춤 예약(12:10·13:40·23:10·00:40 KST) + 3시간 심장 박동 → `verify_publish.py --github`. `contents: write` 만, 비밀값·pip 없음 |
| 상태 브랜치 `alerts-state` | `verify_publish.json`(계산 상태) + `outbox.json`(Worker 가 읽는 계약 `alerts-outbox/1`) — 한 커밋, 강제 push 없음 |
| Cloudflare Worker(레포 밖) | outbox 검증·전송·순서·이력. 토큰은 여기에만. `/acks`·`/failed` 로 끝난 사건의 (id, 보낸 본문 해시)를 공개한다 |
| 맥 | `--preview`·`--dry-run`(쓰기 없음)만. `runner_launch.py` 의 `publish` 진입점은 지웠다 |

- **id** = sha256(`kind|key|extra`) 앞 32 hex, 사건마다 `hash` = sha256(문장). `key` 는 순서 단위: 글 경로 / `us:2026-11-10` / `sys:<kind>`.
- **outbox 에 실린 사건은 전송됐을 수 있다.** 대기 중 미발행 경고를 취소하고 「늦은 발행」으로 바꾸는 길은 GitHub 계산에서 쓰지 않는다.
  경고 뒤 글이 오면 언제나 「앞서 생성된 미발행 경고(기준 …)가 풀렸어요」 — 받았다고 단정하지 않는다.
- **outbox 에서 빠지는 것은 Worker `/acks`·`/failed`(`alerts-acks/2`·`alerts-failed/2`)에 id 와 본문 해시가 둘 다 나온 사건뿐.**
  못 읽거나, 주소가 비어 있거나, 모르는 판(옛 `/1` 포함)이면 아무것도 빼지 않는다. **같은 id·다른 해시는 남긴다** — Worker 가 보낸 것은
  옛 본문이고 지금 본문은 간 적이 없다(codex 구현 1회 #3). 그런 사건은 outbox 에 계속 실리고 Worker 가 거부·경보한다(사람이 본다).
  빠진 사건은 상태에 `sent`·`failed` 로 확인 시점부터 60일 남는다(같은 사건을 다시 만들지 않게). 상태를 새로 시작해도
  계산 **뒤에** 전송 확인을 적용해, 문장이 그대로인 알림은 다시 싣지 않는다. 문장이 달라진 것(정정 횟수 줄 등)은 위 규칙대로 남는다.
- **상한**(사건 500·문장 3,900자·파일 256 KB)은 outbox 로 옮길 때 지킨다. 자르지 않는다: 양이 넘으면 오래된 쪽을 싣고 나머지는
  상태에 대기로 남기며, 너무 긴 문장은 `oversize` 로 상태에만 둔다. 둘 다 `sys:overflow` 사건 하나로 알린다.
  계약의 kind 목록에 overflow 가 없어 지금은 `gap` 으로 싣는다(`publish_watch.OVERFLOW_KIND`) — 계약이 정해지면 그 상수만 바꾼다.
- **push 거절** = 다른 실행이 먼저 올림 → main·상태 브랜치를 둘 다 다시 받아 처음부터 계산(거절 3회까지). 인증·네트워크·원격 거부·
  「브랜치 조회 실패」는 바로 실패(0 아닌 종료). 조회 실패를 「브랜치 없음 = 처음 실행」으로 읽지 않는다(`ls-remote --exit-code`).
- 브랜치가 없으면 첫 실행 = 기준선. 브랜치는 있는데 상태 파일이 없거나 손상이면 전부 다시 계산하고, 손상본은
  `verify_publish.corrupt-<시각>.json` 으로 브랜치에 남긴다.
- `last_ok` 는 계산이 정상 끝난 회차에만 전진하고 push 돼야 보인다. Worker 로의 `POST /poke` 는 push 성공 뒤에만, 실패해도 기록만.
- 문장의 확인 주체는 `who`: GitHub 계산은 「[GitHub이 직접 대조]」·「GitHub 이 짝만 다시 확인했어요」, 맥 미리보기는 「맥」. 지문은 주체와 무관.
- 매일 요약은 `origin/alerts-state:verify_publish.json` 을 읽어 `publish_watch.summary_lines_from(st, now)` 에 넘긴다
  (GitHub 상태에는 `stale=GITHUB_STALE` 9시간 — 2시간 기준이면 심장 박동 간격만으로 매일 「n시간 전」이 뜬다).
- 한계: 한 실행은 그 시점 최신 main 의 **최종 상태**를 알린다(실행 사이 A→B→A 는 안 보일 수 있다). 예약은 2~5시간 늦을 수 있어
  미발행 경보도 그만큼 늦는다. 계산 코드는 AI 가 고칠 수 있다 — 거짓 알림·누락은 가능하고, 토큰은 못 가져간다.
- 시험: `scripts/review/tests/test_publish_github.py`(원격은 로컬 bare 레포).

When changing this: read this spec before touching `scripts/verify_publish.py`, `scripts/review/publish_watch.py`, `scripts/review/prepub_view.py` or `scripts/verification/repo_check.py`.

## 이유를 붙인다(2026-11-11 사용자 지시)

「대조 불가 6개」 알림을 받고 그게 뭔지 물어야 했다 — 사용자: 「실패했다고만 말하지 말고 그 이유까지 첨부해줘」.
발행 건별 알림(`prepub_view.render_publish`)은 상태어 옆에 항목과 이유를 둔다: 칸마다 `repo_check.cat_why` 의 첫 이유,
작업 공간 전용 입력은 파일 이름(최대 8 + 외 N)과 「원본을 보관하지 않았다」, 검사기마다 기록의 `reason` 또는 상태에 맞는
`items` 2개(100자), 자동 대조하지 못한 수치는 `numbers.unverified_by`(check_numbers 의 고정 분류 이름·정수) 상위 4개.
이유가 없으면 「이유가 기록에 없어요」. 이유 문장 상한 1,800자(사건 3,900자 안). **쓰는 값은 공개 레포 기록에 이미 있는 것뿐**
(outbox 도 공개 브랜치). 맥 요약 줄(`digest_lines`)은 기존 계약대로 칸 이름·고정 분류만 — 검사기 원문을 싣지 않는다.
판정(`anomalies`·`clean`·`fingerprint`)은 바꾸지 않았다 — 표시용은 `anomaly_labels`. 이미 만든 사건의 본문은 다시 쓰지 않는다.
`publish_watch`: 미발행은 그 시각 레포 수집 판(`report_date`·`complete`)으로 갈래를 나누되 원인을 단정하지 않는다, 사라짐은
지운 커밋, 기준점 끊김은 조상 아님/객체 없음, 요약 꼬리는 휴장 달력 못 읽은 이유·마지막 실패 사유·미전송 앞 3건.
