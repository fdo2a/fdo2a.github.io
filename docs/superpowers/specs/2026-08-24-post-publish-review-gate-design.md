# 발행 후 codex 사후 검토 게이트

2026-08-24 사용자 지시. 커밋·발행 전 codex 검토를 상시 규칙으로 삼되, 클라우드 루틴이
자동 발행하는 브리프는 codex CLI가 로컬에만 있어 발행 앞에 검토를 끼울 수 없다.
그래서 검토를 **발행 뒤**로 옮기고, 잊지 않도록 상태 파일로 기계화한다.

## 왜 사후인가

codex는 로컬 CLI(`~/.local/bin/codex`)다. 클라우드 러너에서 돌지 않는다. 선택지는
셋뿐이었다.

1. **사후 검토** — 루틴은 그대로 08:00에 발행하고, 로컬 세션을 열 때 검토·정정한다.
   몇 시간 미검토판이 노출되는 것이 대가.
2. **발행 보류** — 루틴이 글만 쓰고 공개는 사람이 한다. 매일 정시 발행이라는 전제가
   깨진다. 기각.
3. **클라우드 2차 리뷰어** — 루틴 안에 검토 서브에이전트를 넣는다. codex가 아니라
   같은 계열 모델이라 눈이 덜 다르고 토큰만 는다. 기각.

1을 택했다. 정정은 «발행 취소»가 아니라 «정정 커밋»이라 되돌리기 어려운 작업이 아니고,
[verify_post.py](../../../scripts/verify_post.py)라는 손편집 안전망이 이미 깔려 있다.

## 격리 — codex와 Claude가 같은 파일을 안 만지게

사용자 지시: 「검토는 반드시 읽기 전용으로 시키거나, 워크트리로 작업 폴더 자체를
분리해서 각자 다른 브랜치에서 일하도록」. 용도별로 나눠 둘 다 쓴다.

| 용도 | 샌드박스 | 작업 폴더 | 고치는 손 |
|---|---|---|---|
| **발행본 검토** (매일) | read-only | `site/` (main) | Claude |
| **막힌 문제 위임** (가끔) | workspace-write | `site/.claude/worktrees/fix-<topic>` (`fix/<topic>`) | codex |

읽기 전용은 약속이 아니라 강제다 — codex-companion은 `--write` 없이 부르면
`sandbox: "read-only"`로 실행해 프로세스가 물리적으로 쓰기를 못 한다. 검토 경로에서는
`--write`를 **절대** 붙이지 않는다.

위임 경로만 워크트리를 판다. 브랜치가 갈리므로 codex가 커밋해도 main의 내 작업과
겹치지 않고, 병합은 내가 diff를 본 뒤에 한다.

## 무엇을 검토하는가

기존 게이트(`check_macro`·`check_stance`·`check_thesis`·`verify_post`)가 기계적 검사를
이미 한다. codex는 스크립트가 못 보는 것을 본다.

1. **데이터 ↔ 본문 정합** — `data/*.json`의 실제 값과 서술이 어긋나는 곳. 게이트는
   숫자가 *있는지*만 보지 *맞는지*는 못 본다. 2026-08-17 발행본이 실업수당 청구
   **감소**를 「뚜렷하게 나쁜 방향」이라 정반대로 쓴 것이 이 부류다.
2. **논리·해석 비약** — 근거 없는 단정, 데이터가 지지하지 않는 결론, §8 레짐·§9 스탠스
   승계 규율(하루 한 단계·대각선 금지) 위반.
3. **문장·가독성** — CLAUDE.md 문체 규칙(한 문단 한 주제, 피동 반복, 기계적 나열).

레이아웃·HTML은 뺀다. `verify_post.py`가 Playwright로 390·1280px를 이미 본다.

## 상태 — 무엇이 미검토인가

`reviews/index.json` 하나가 원장이다. 감시 대상 파일마다 **검토 당시 blob SHA**를 적는다.

```json
{
  "reviewed": {
    "posts/2026-08-22.html": {"sha": "a1b2c3…", "at": "2026-08-24T14:03:00+09:00", "findings": 3}
  }
}
```

미검토 = 원장에 없거나(신규), 원장의 SHA와 현재 SHA가 다른(수정됨) 파일. blob SHA는
내용 주소라 「나중에 손으로 고친 글이 자동으로 다시 큐에 들어온다」는 성질이 공짜로
딸려온다. 날짜나 순번을 따로 관리할 필요가 없다. (`/thesis/` 페이지는 아래 예외에 따라
감시 대상이 아니므로 이 성질도 적용되지 않는다 — 그쪽은 `--check`가 맡는다.)

### 감시 대상은 열려 있다

감시 대상을 «`posts/`·`kr/posts/`·`thesis/`» 화이트리스트로 잡았다가 뒤집었다. 지금
설계 중인 주간·월간 정리가 `/weekly/`·`/kr/weekly/`·`/comment/`·`/monthly/`·
`/kr/monthly/` 다섯 경로를 새로 쓰는데, 화이트리스트였다면 그 다섯이 **아무 소리 없이**
게이트를 통과했을 것이다. 검토를 빠뜨리는 것이 비싼 실패고 큐에 한 줄 더 뜨는 것은 싼
실패이므로, 실패 방향을 싼 쪽으로 돌린다.

그래서 **`.html`이면 일단 감시 대상**이고, 기계가 쓴 조각과 내비게이션만 뺀다.

- 경로에 `data/`·`scripts/`·`assets/`·`node_modules/`·`_workspace/`가 있으면 제외
  (생성된 조각과 테스트 픽스처)
- 파일명이 `index.html`·`404.html`이면 제외 (내비게이션)
- `.html`이 아니면 제외 (`posts.json`·`sitemap.xml`·`data/*.json`은 사람이 읽는 산문이
  아니다)

새 HTML 파이프라인은 코드를 고치지 않아도 자동으로 들어온다.

**예외 하나 — 매일 렌더되는 페이지** (2026-08-25): `/thesis/`는 수집 워크플로가 매일
`content.py`의 산문과 그날 `watch.json`의 수치로 다시 렌더한다. 그대로 두면 시세가
움직인 날마다 네 건이 큐에 오르는데 바뀐 것은 숫자뿐이라 읽을 것이 없다. 그래서 그
경로의 `.html`은 감시에서 빼고, **그 페이지가 렌더되는 원고**를 대신 본다.

- `scripts/thesis/content.py`·`narrative.py`·`render.py` — 사람이 쓴 문장
- `thesis/data/thesis_state.json` — changelog가 손으로 쓰이고 페이지에 실린다

이 두 목록은 손으로 관리한다. 새 산문 파일이 생기면 `_PROSE_SOURCES`에 넣어야 한다 —
HTML 쪽의 «자동으로 들어온다»가 여기서는 성립하지 않는다.

손으로 페이지를 고치는 경우는 이 게이트가 아니라 `build_thesis_pages.py --check`가
막는다. 수집 워크플로가 **수집 전에** 커밋된 페이지와 커밋된 데이터로 렌더한 결과를
대조한다. 수집 후에 대조하면 그날의 정상적인 시세 변화까지 걸리고, 렌더를 먼저 돌리면
손편집을 잡는 게 아니라 덮어써 버린다.

### 두 눈으로 본다 — 발행된 판과 작업 폴더

`origin/main`만 보면 방금 손으로 고쳐 아직 push하지 않은 글을 놓친다. 작업 폴더만 보면
루틴이 올린 오늘치를 놓친다. 처음엔 origin 트리 위에 작업 폴더를 **덮어썼는데**, 그러면
제일 위험한 경우가 사라진다 — 노트북이 며칠 뒤처져 있고 루틴이 같은 날짜 글을 정정
재발행했다면, 로컬에는 「검토 완료된 옛 판」이 있고 그것이 새 판을 가린다. 발행본 규칙이
«같은 날짜는 REPLACE»라 실제로 일어나는 일이다.

그래서 덮어쓰지 않고 **두 트리를 각각 원장과 대조한 뒤 합집합**을 낸다. 어느 쪽이든
원장이 모르는 내용을 담고 있으면 미검토다. 합칠 때는 경로가 아니라 **(경로, SHA)**로
중복을 제거한다 — 경로로만 묶으면 원장이 모르는 두 판 중 하나가 목록에서 사라지고,
사라진 쪽이 하필 공개돼 있던 판일 수 있다.

`git ls-tree`·`git diff`·`git ls-files`는 전부 `-z`로 받는다. 기본 출력은 공백·따옴표·
한글이 든 경로를 C 문자열로 따옴표 처리해 내보내서, 그대로 쪼개면 실제와 다른 키가
만들어진다.

**시딩**: 도입 시점에 감시 대상 전부를 현재 SHA로 원장에 넣는다(`baseline: true`).
과거 50편이 첫날 큐에 쏟아지는 것을 막고, 이후 발행·수정분만 자연히 들어온다.

## 발동 — 세션 시작 훅

`SessionStart` 훅이 `review_gate.py pending --hook`을 돌려 미검토 목록을 컨텍스트에
넣는다. 훅은 알리기만 하고 검토를 자동 실행하지는 않는다 — 무관한 작업을 하러 연
세션까지 검토가 선행되면 곤란하다.

훅은 `git fetch`를 10초 타임아웃으로 시도한다. 아직 pull하지 않은 오늘치 발행본을
놓치지 않기 위해서다. **fetch가 실패했으면 미검토가 0건이어도 그 사실을 말한다** —
「미검토 없음」이 「네트워크가 없어서 못 봤음」의 다른 말이면 게이트가 아니라 착각이다.

훅은 **어떤 경우에도 exit 0**이고, 동시에 **조용히 죽지 않는다.** 원장이 깨졌거나 git이
이상하면 예외를 삼키지 않고 `[검토 게이트] 확인 실패 — …`를 출력한다. 세션 시작 훅에서
조용한 실패는 게이트가 영영 꺼진 것과 같은데, 그건 눈에 띄지 않는다.

훅 배선은 `/Users/daeyoung/Desktop/report/.claude/settings.json`에 있다. 레포 밖이라
버전 관리 대상이 아니다(CLAUDE.md와 같은 처지). 로직은 전부 레포 안에 있고 배선만
로컬이다.

## 절차

`.claude/REVIEW_GATE.md`에 있다. 요약하면:

`git pull --rebase` → codex 읽기 전용 검토 → 지적 검증(틀린 지적 기각) → main에서 수정
→ `verify_post.py` → `review_gate.py mark` → 커밋·푸시.

`verify_post.py`가 수정된 수치를 「움직였다」고 잡는 것은 정상이다. codex가 틀린 숫자를
찾아 고쳤다면 그게 바로 걸려야 할 자리이고, 의도한 정정임을 눈으로 확인하고 넘어간다.

**원장에 남는 SHA는 정정 후 내용이다.** codex가 읽은 것은 정정 전 판이므로, 정정하면서
새로 넣은 오류는 이 게이트가 다시 잡아주지 않는다. 정정 전 SHA를 남기면 그 글이 영영
큐에 남으므로 이렇게 뒀고, 대신 정정은 **최소 범위**로 하고 반영한 지적 하나하나를 눈으로
확인하는 것이 절차의 일부다(4~5단계).

## 이 설계가 codex 검토에서 고쳐진 것

첫 판을 codex에 읽기 전용으로 검토시켜 13건을 받았고, 그중 아홉을 반영했다. 값이 컸던
것은 셋이다 — **감시 화이트리스트가 새 파이프라인을 통과시킨다**(위 「감시 대상은 열려
있다」), **작업 폴더 덮어쓰기가 뒤처진 노트북에서 발행본을 가린다**(「두 눈으로 본다」),
**fetch 실패와 원장 손상이 훅을 조용히 무력화한다**(「발동」). 셋 다 게이트가 «켜져 있는
것처럼 보이면서 꺼져 있는» 종류라, 사후에 눈으로 발견되기 어려웠다.

기각한 것도 적었다. `seed --force`가 읽지 않은 글을 「본 것」으로 남길 수 있다는 지적은
의도된 탈출구라 경고 문구만 붙였고, 원장 JSON의 중복 키 처리는 실제로 일어나지 않는다.

고친 코드를 **한 번 더** 읽혀 네 건을 더 잡았다. 합집합이 경로로 중복을 제거해 같은
글의 다른 판을 버리던 것, `seed`가 `origin/main`이 없는 레포에서 잘못된 ref를 넘겨
커밋 안 한 수정분을 기준선에서 빠뜨리던 것, `mark`가 레포 밖 경로를 받아 죽은 줄을
남기던 것, `--hook --json` 조합의 종료 코드. 첫 검토가 설계를 고쳤다면 두 번째는
**첫 검토를 반영하다 새로 넣은 것**을 잡았다 — 정정이 정정을 낳는다는 것이 이 게이트가
`verify_post.py`를 절차에 끼워 둔 이유이기도 하다.

## 열린 항목

- 검토 지적의 상세 내역은 커밋 메시지에만 남는다. 「어떤 유형 지적이 반복되는가」를
  집계하려면 별도 기록이 필요하지만, 그 필요가 실제로 생기기 전에는 만들지 않는다.
- 백로그가 쌓였을 때(여행 등) 며칠치를 한 번에 검토할지, 최신 것만 볼지는 그때 판단.
