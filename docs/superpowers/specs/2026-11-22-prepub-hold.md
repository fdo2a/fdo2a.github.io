## 무엇이 바뀌었나
1. **발행하는 길은 하나**: 검토 도착 → 정확성 지적 전부 판정·반영·게이트 재통과 → `prepub_review.py facts-done` → `record`(표시가 없으면 exit 10, 기록을 쓰지 않는다). 그 밖의 모든 실패는 `PREPUB_REVIEW.md` §5 로 세운다. 원래 판으로 되돌려 발행하는 길은 지웠다(`test_hold_docs.py` 가 지킨다).
2. **세우기(`prepub_review.py hold`)**: 닫힌 칸만 든 보류 기록(섹션·날짜·요청 id·상태·우리가 만든 이유·`hold`·시각)을 커밋하고, 잠금을 어떻게 놓을지 알린다.
   - 검토가 아예 돌지 않음(`NOT_RUN` — 제출 실패·한도·마감·결과 못 읽음·`stale_html`·`mark_failed`) → `release`. 받아들인 것이 없으니 재시도가 처음부터 써도 잃는 것이 없다.
   - 판정을 시작함(`recovery_needed`·`style_abort`·`facts_unmarked`, 모르는 값) → `run_lock.sh hold`. 재료(제출 판·검토 답·고치던 판)는 비공개 `review-runner` 의 `holds` 가지에만.
3. **판정 중 표시는 잠금 ref 에**: `facts.md` 를 읽기 전에 `run_lock.sh renew <키> judging`(수정 전 `fixing`). 표시는 뒤의 renew 가 이어 달고, 브리프 push 직후 `renew … clear` 로 뗀다. 세션이 판정·수정 중에 죽으면 stale 이어도 acquire 가 exit 6 — 재시도가 처음부터 다시 쓰지 않는다. `held`·죽은 표시는 `routine_due.py` 가 `HOLD`(재시도 관문은 쏘지 않는다). 사람만 `run_lock.sh unhold`.
   - 왜 main 의 기록 파일이 아니라 잠금 ref 인가: 런 중간에 main 에 push 하면 발행 커밋의 `git add -A`·`pull --rebase` 와 같은 경로에서 부딪친다. 잠금 ref 는 이미 런마다 쓰는 자리이고, acquire·routine_due 가 이미 읽는다.
   - 판정 표시는 첫 글(브리프)이 없을 때만 HOLD 로 읽는다 — 브리프가 나간 뒤 남은 표시가 뉴스 이어 쓰기를 막지 않게.
4. **초안은 비공개로**: `submit.py` 가 공개 `review-drafts` 대신 비공개 `review-runner` 의 `drafts` 가지에 Git Data API(`gh api`)로 올린다. 막기 모드에서는 세운 초안이 공개 가지에 남아 「검토 안 된 판의 공개」가 되기 때문이다. 비공개 워크플로는 자기 레포에서 먼저 읽고, 11/22 전 제출분만 공개 가지에서 읽는다.

5. **codex 구현 검토 1회차(IMPL NO) 반영**:
   - 보류 기록 push 는 `hold --push` 가 origin/main 위에 **그 파일 하나만** 바뀐 커밋을 따로 짓는다 — 문체 마감 B 의 `git add -A` 나 이미 만든 발행 커밋이 섞이지 않는다(시험: 스테이징·로컬 커밋 뒤 push 한 나무 = 원래 + 기록).
   - `record --html posts/D.html` 은 올릴 파일이 `facts-done` 판이나 봉인한 판(`seal --why style|note` — guard 를 지난 문체 편집·에디터 노트)과 바이트가 같을 때만 받는다. 작성자가 다시 쓴 판은 루틴이 받아들인 지적을 다시 대조하고 `facts-done` 을 다시 찍어야 한다(앞 봉인은 무효).
   - 판정 표시가 달린 클론의 `release` 는 풀지 않고 `held … reason=recovery_needed` 로 바꾼다 — 지시문의 어느 중단 경로가 release 를 불러도 재시도가 처음부터 쓰지 않는다.
   - 브리프 push 와 `clear` 사이에 죽은 흔적은 `acquire … brief-out`(부른 쪽이 origin/main 의 브리프를 확인) 으로만 넘겨받는다. 세움(`held`)은 그래도 열리지 않는다.

6. **codex 구현 검토 2회차(IMPL NO) 반영**:
   - (2·3회차 #1) 판정 표시를 로컬 파일에 따로 적지 않는다. `renew`·`release` 는 **lease 를 거는 바로 그 잠금 커밋(소유 SHA)의 제목**에서 표시를 읽는다 — push 는 원격 끝이 그 커밋일 때만 통과하므로, 통과한 새 커밋의 표시는 언제나 직전 원격 커밋의 표시에서 나온다. 같은 클론의 renew 가 겹쳐도 파일과 원격이 어긋날 자리가 없다(2회차는 「성공 뒤 표시 기록」의 틈, 3회차는 그 틈을 막느라 넣은 「실패 뒤 표시 되돌리기」의 틈을 짚었다 — 두 번 같은 갈래라 파일을 없앴다). 소유 SHA 가 가리키는 커밋을 못 읽으면 renew 는 exit 3, release 는 exit 4(잠금을 움직이지 않는다).
   - `record` 의 공개 인용(`style_findings`·`clarity`)은 제출 초안이 아니라 **`--html` 로 받은 올릴 판**(해시를 잰 바로 그 바이트)과 대조한다 — 고치면서 지운 글자는 빈 인용이 된다. 따라 오는 것: 반영된 문체 수정의 인용은 늘 비고, 주간 묶음(`style_digest`)은 빈 인용을 「인용이 빈 지적 N건」·잔존 「알 수 없음」으로 읽는다(분류 집계는 그대로).
   - STEP 0 의 exit 6 갈래는 설정하지 않은 `KEY` 대신 `/tmp/us-lock-key` 에서 날짜를 읽는다(`cut -d- -f2-`). 같은 파일의 국채 종가 대기 줄에 남아 있던 `renew "$KEY"`(이 변경 전부터 있던 것)도 같은 꼴로 고쳤다.
   - 발행 전 검토의 문체 후보가 0 인 날 STEP 2.6(기본 꺼짐)이 켜져 글을 고치면 ORCHESTRATOR STEP 2.6 이 그 판을 `seal --why style` 로 봉인한다 — 없으면 `record` 가 exit 10 으로 멀쩡한 글을 세운다. KR 은 `PREPUB_DIR` 이 없어 공용 `STYLE_CLOSE.md` 가 아니라 US 지시문에 둔다.

## 같은 실패로 처음부터 다시 쓰기를 되풀이하지 않는다 (선행 묶음 ②, 2026-11-22 밤)
사용자 11/22: 「다시 루프로 돌아가서 문제인걸 수정하고 최종 발행까지」 → 자동 이어 하기 설계(로컬 `plans/attachments/2026-11-17-prepub-all/auto_resume_design_v1.md`, codex 설계 5회 상한 뒤 사용자 「받아」)의 첫 조각. 본체(재료 꾸러미·`plan`·받아들임 장부)는 11/24 첫 실행으로 비공개 쓰기를 확인한 뒤.
- 구멍: 「검토 미실행」 15종이 전부 `release` 라, 다시 해도 똑같이 실패하는 부호가 슬롯마다(하루 최대 8번) 수집·Opus 작성·제출을 처음부터 다시 했다. 세는 곳이 없었다.
- `cmd_hold --push` 가 origin/main 의 같은 날짜 기록을 읽어 센다(닫힌 칸 `attempt`·`last_counted`, 날짜가 키라 세션이 넘어가면 새로 센다). 갈래: 사람 손 `auth_missing` = 첫 번째에 세움 / 기다림 `limit` = 세지 않고 늘 `release`(횟수는 그대로 옮긴다) / 나머지 13종 = 같은 부호 연달아 2번 또는 3번째면 세움.
- 셀 수 없으면 막는 쪽: 앞 기록을 못 받았거나 꼴이 모르는 것이면, 또는 이번 기록 push 가 실패하면(다음 런이 횟수를 못 본다; 어떤 예외든) 세는 실패는 세움이다. 파일이 없는 것은 「그날 첫 실패」다. 못 센 런은 횟수를 0 이 아니라 `attempt: null`(모름)로 남기고, 그 뒤로도 기록을 지울 때까지 모름이다.
- 읽기와 올리기는 한 받기다(codex 구현 2회차 뒤 모양을 바꿨다): `push_record(build=)` 가 받을 때마다 **그 커밋의** 같은 파일을 읽어 기록을 다시 짓고 그 커밋 위에 올린다. 거절되면 다시 받아 다시 센다 — `lock=` 은 실제로 올라간 회차의 판정이다. 받기가 실패하면 올리기도 없다(「읽기만 실패·덮어쓰기는 성공」이 없다).
- 아는 꼴은 **`cmd_hold` 가 쓰는 세움 기록 그대로**뿐이다(`_carried` — 칸 집합 상수 `HOLD_KEYS_M`·`HOLD_KEYS` 를 쓰는 쪽과 함께 본다): 파일 없음 / M 의 세움 기록(7칸) / 이 묶음의 기록(9칸, 세는 부호면 `last_counted == state`·`attempt ≥ 1`, 0번 ⇔ 마지막 부호 없음). 섹션·날짜·`reason`·`request_id`·`recorded_at`(실제 시각)도 맞아야 하고, **파일 바이트가 `_write` 가 쓰는 글자와 같아야 한다**(git 출력을 다듬지 않고 읽는다 — 손으로 고쳐 줄바꿈 하나만 붙어도 셀 수 없음이다). 그 밖의 모든 것과 해석 중의 어떤 예외든 「셀 수 없다」. **발행 기록도 셀 수 없음이다**(설계 §6.1 의 「발행 기록이면 1번째」에서 막는 쪽으로 바꿨다 — 이미 발행한 날짜를 또 세우는 일은 정상 흐름에 없고, 칸 20여 개의 값을 따지는 검사는 codex 3회차까지 매번 뚫렸다).
- 한도(`limit`)는 읽지 못한 기록을 덮어쓰지 않는다 — 올리지 않고(`pushed=skipped`) `release`. 실제 횟수가 그 기록에 있을 수 있어서다. 판정 뒤 부호와 세는 실패는 읽지 못해도 올린다(세움이니 사람이 부호를 본다).
- 세움은 지금 있는 `lock=hold:recovery_needed`(진짜 부호는 기록 `state`). `run_lock.sh`·`routine_due.py`·`retry_gate.py`·`ORCHESTRATOR.md`·비공개 러너는 그대로. `--push` 없이 부르면 원격을 읽지 않고 M 그대로다(로그인 없음도 `release` — §5 는 늘 `--push` 로 부른다). 판정 뒤 부호는 M 의 순서(비공개 재료 → 공개 기록) 그대로, 세는 규칙으로 세운 것은 기록 push 가 판정을 정한 뒤 재료를 올린다. `hold --date` 는 실제 날짜(`YYYY-MM-DD`)만 받는다.
- 사람이 풀 때 기록 파일이 남아 있으면 다음 실패가 곧바로 세움이 된다 — `PREPUB_REVIEW.md` §5 에 「원인을 고친 뒤 기록도 지운다」.
- codex 구현 4회차 뒤: 재료 저장의 어떤 예외든 `materials=failed` 로 삼키고 `lock=` 줄까지 간다. 기록 push 가 반영됐는데 실패로 돌아오면 다시 받은 머리가 그 커밋인지 보고 다시 세지 않는다. 로컬 기록은 재료 업로드보다 먼저 쓴다(M 의 순서).
- codex 구현 5회차(상한) 뒤 사용자 「고쳐서 받아」 — **codex 재검토 없이** 두 곳: 칸 순서가 쓰는 순서(`HOLD_ORDER_M`·`HOLD_ORDER`)와 다르면 셀 수 없음(다시 직렬화는 읽은 순서를 따라 순서 차이를 못 잡았다), 앞 기록 blob 읽기만 실패하면 「셀 수 없음」으로 지어 올린다(판정 뒤 부호의 공개 기록이 M 처럼 올라가고, 세는 실패는 세움, 한도는 올리지 않는다).
- **남은 구멍(이 묶음이 닫지 않는다)**: 공개 기록은 올라갔는데 세움 명령(`run_lock.sh hold`)이 실패하면 — 잠금 push 거부(exit 5, §5 가 한 번 더 부른다)나 소유 파일 없음(exit 4) — 세움이 서지 않아 120분 뒤 재시도가 다시 쓴다. M 의 판정 뒤 부호도 같은 길이다. 닫으려면 재시도가 쓰기 전에 같은 날짜 기록을 읽어야 한다 — 본체(`plan`)의 몫. 그때까지는 다시 쓴 런의 다음 실패가 횟수(`attempt`)로 다시 세워진다.

## 글 막힘 알림 — 세운 글을 몇 분 안에 텔레그램으로 (2026-11-22 밤)
설계: 로컬 `plans/attachments/2026-11-17-prepub-all/instant_telegram_design_v1.md` v1.4(codex 설계 5회 상한, §14 의 세 지적은 구현에서 고쳤다). 새 길은 없다 — 지금 있는 outbox → Worker 길을 쓰고, **Worker 는 고치지 않는다**(사건 종류는 기존 `missing`).

**쓰는 쪽 — 보류 기록의 닫힌 칸 `next`**(`prepub_review._hold_rec`)
- 셋째 꼴 = 횟수 꼴 + `next`(`HOLD_ORDER_N`, 10칸). 새 런은 셋째만 쓴다. `_carried` 는 세 꼴을 다 받는다 — 칸 순서·키 집합·값(`next ∈ NEXT_VALUES = (retry, person)`) 검사를 모두 지나야 하고, `next` 는 횟수(`attempt`·`last_counted`)에 들지 않는다. 옛 두 꼴의 읽기와 세는 결과는 그대로다.
- `next` 는 `_hold_rec` 가 한 번 정한다: 판정 뒤 부호 → `person` / 검토 미실행 부호는 `--push` 이고 (세는 규칙이 세움이거나 `auth_missing`)일 때만 `person`, 아니면 `retry`. `cmd_hold` 의 `lock=` 은 이 값에서 나온다(`person` → `hold:…`, `retry` → `release`). 덮는 것은 하나 — `pushed=failed` 인 세는 실패는 `hold`(그 기록은 main 에 없다). 시험이 부호 18 × 앞 기록 경우 × `--push` 유무의 모든 줄을 지킨다(`scripts/prepub/tests/test_hold_next.py`).

**깨우기** — `publish-watch.yml` 의 push 경로에 `reviews/prepublish/**`. 발행 때의 `reviewed` 기록은 글과 같은 push 라 실행이 늘지 않는다.

**감시 쪽**(`publish_watch._hold_scan`, `build_outbox`)
- 대상 `HOLD_SECTIONS = ('us',)` — 다른 섹션은 발행 전 검토가 붙는 날 한 줄을 더한다. key `hold:<섹션>:<날짜>`(세션 사건 `us:<D>` 와 다른 줄 — Worker 는 key 마다 순서를 지킨다).
- 살아 있는 막힘 = 이번 판의 `reviews/prepublish/<섹션>/<D>.json` 중 파일 이름이 실제 날짜이고 오늘(KST)에서 7일 안, `hold is True`, `state ≠ reviewed`, 그 날짜 글이 이 판에 없다. 기록에서 꺼내는 값은 넷(`state`·`next`·`attempt` 0-99·`recorded_at`)이고 각각 검증한다 — 틀리면 그 칸만 「모름」이고 사건은 만든다(KST 변환 넘침 포함).
- 회차: 상태의 `holds[key] = {n, sig, live}`, 서명 = `state|next`(모름은 `?`). 살아 있고 서명이 같으면 아무것도 안 한다 — 한도로 슬롯마다 다시 세워도 한 번. 다르거나 살아 있지 않았으면 `n += 1` 하고 사건 `missing`·extra `held|<born>|<n>`·표시 `held: n`. `born` 은 **무작위 값**(`secrets.token_hex`) — 상태를 잃고 같은 초에 다시 시작해도 옛 사건 번호와 겹치지 않는다. 처음 실행(기준선)은 보내지 않는다.
- 대조 하나: 이번 훑기의 살아 있는 목록에 없는 막힘(글이 올라옴·`reviewed`·삭제·서명 바뀜·7일 창 밖)의 대기 사건은 `cancelled`. **이번 실행이 살아 있다고 확인한 막힘만 싣는다**(`HOLD_SHIP` — 상태 파일에 저장하지 않는다, 읽기 실패로 일찍 돌아간 실행과 훑기만 실패한 실행은 아무것도 싣지도 닫지도 않는다). 훑기의 어떤 예외든 기존 판정에 닿지 않는다.
- 막힘 칸은 **공용 검증(`_validate`) 밖**에서 따로 본다 — 그 칸만 깨졌으면 `holds`·`born` 만 새로 만든다(상태 전체 초기화·손상 복사본 없음). 둘을 함께 새로 만들어야 회차가 1 부터 다시 시작해도 번호가 안 겹친다.
- 기록을 읽는 길은 하나(`_json_top` — 글자 전체의 JSON 문법을 재귀 없이 검사하고 맨 위 층만 꺼낸다, 숫자는 0-99 만 변환). 결과는 셋: 읽힌 세움 / 읽혔지만 세움 아님(살아 있지 않다) / **못 읽음**(문법·UTF-8 이 틀림, `hold`·`state`·`next` 가 두 번) — 못 읽은 기록은 살아 있다고 보고 값은 전부 모름으로 알린다(잘린 세움 기록을 조용히 넘기지 않는다). 그 서명은 `?|?|<blob id 16자>` 라 바이트가 바뀔 때만 새 회차이고, 알림 글에는 싣지 않는다. 회차 번호는 이력에 남은 사건 번호를 다시 쓰지 않는다.
- 상태 파일의 막힘 두 칸은 공용 해석 **전에** 바이트에서 바깥 경계만 찾아 떼고(`_split_hold_fields`) 따로 읽는다 — `loads_state` 가 돌려주는 상태에는 두 칸이 검증을 지난 채 둘 다 있거나 둘 다 없다. 막힘 칸 밖의 손상은 종전대로 상태 전체 손상이다.
- codex 구현 검토는 5회 상한(1·2회 terra, 3-5회 sol high — 모두 NO, 회차마다 앞 지적은 닫힘). **상한 뒤 사용자 결정(「고쳐서 받아」)으로 고친 두 곳 — 쓰지 않는 칸의 중복은 읽기에 닿지 않게 한 것, 상태 파일 막힘 칸을 바이트 경계로 떼는 것 — 은 codex 미검토다.** 5회차의 범위 밖 제안(막힘이 모두 취소된 뒤에도 막힘 넘침 안내가 다시 실림)은 받지 않았다.
- outbox: 기존 사건 계산은 막힘이 없을 때와 같다. 막힘은 기존 사건을 다 실은 뒤 남은 자리에만, 막힘 때문에 생기는 넘침 알림도 남은 자리에 들어갈 때만 — 기존 사건(과 그 넘침 알림)의 자리를 차지하지 않는다. 생산자의 싣는 순서는 Worker 의 key 간 전송 순서를 정하지 않는다.
- 문구는 닫힌 표에서만(`HOLD_REASON` 18개 = `NOT_RUN ∪ HOLD_CODES`, `HOLD_NEXT_TEXT`). 기록의 `reason`·요청 id·그 밖의 글자, codex 문장·초안은 싣지 않는다. 날짜는 파일 이름, 시각은 검증한 값을 KST 로 다시 지은 것. 맥 요약 이름표는 「US 일간 M/DD 글 막힘」.
- 따로 「풀림」 알림은 없다 — 글이 올라오면 지금 있는 발행 알림(그리고 12:10 「미발행」이 나갔던 날은 「미발행 해소」)이 닫는다. 12:10 「미발행」의 원인 줄은 그대로다(번호가 원인 줄 해시에서 나온다).

**못 하는 것**: 기록 push 가 실패했거나(`pushed=failed`) 기록 전에 죽은 세션은 즉시 알림이 없다 — 지금처럼 폰 알림 + 12:10 `missing`. Worker 가 이미 받은 막힘 사건은 취소하지 못한다(글이 올라온 뒤 묵은 막힘이 나갈 수 있다, 그 앞뒤로 발행 알림이 간다). 두 감시 계산 사이에만 있던 중간 서명은 알리지 않는다(마지막 서명만). 보류 기록만의 push 가 실제로 감시를 깨우는지와 도착 시간은 첫 실제 보류에서 확인한다. Worker 계약 문서(`alerts-contract-2.5.md`, 이 레포 밖)의 key 한 줄은 아직 쓰지 않았다.
