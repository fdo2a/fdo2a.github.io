# 발행 전 검증 기록 (2026-11-08)

## 왜

면접 지적: 수치 검증 절차를 눈으로 확인할 수 있어야 하고, 시스템의 실패를 미리 이해·관리해야 한다. 그 전까지
발행 루틴은 검사기 14개 안팎을 돌리고 결과를 버렸다. 매일 검증 알림(`2026-11-08-daily-verify-digest.md`)은 발행
**뒤** 다시 검사한 결과일 뿐이고, US 루틴은 게이트 블록 뒤에도 가독성 수리 루프·STEP 2.6/2.7·편집자 노트가 글을
바꿀 수 있어 「검사한 판」과 「올라간 판」이 다를 수 있었다.

실측(11/08). ① 최근 US·KR 6편을 발행 커밋 데이터로 다시 검사하자 5편에서 실패가 나왔다. ② 원인을 가리려 **충실 재현**
(첫 발행 커밋 C 의 첫 판을 C^ 의 코드·데이터, C 의 연구 원장, C 에서 승격된 책 `data/macro.json`·`kr_stance.json` 으로)을
하자 **그때 있던 검사기는 6편 모두 통과**했다. 남은 「통과 아님」은 그 뒤에 생긴 검사기뿐이다. 실패의 원인은 작업 공간에만
있던 `macro_next.json`, 그 뒤 쌓인 연구 원장(cycle stale), 다음 날 정정된 KR 글과 그날 데이터, 그 뒤 생긴 규칙(실업수당
구조 수치)이었다. **사후 재검사로는 발행 당시를 증명할 수 없다** — 이것이 발행할 때 기록하는 이유다.
(처음 보고에서 「전부 환경 탓」이라 한 것은 3건만 직접 본 결과였다 — codex 구현 검토가 짚었고 충실 재현으로 확인했다.)

## 무엇을 하나

- `config/prepub_gates.json` 이 **현재 실행 목록** 하나다. 검사기마다 `required`(필수/참고), `kind`(format·numbers·
  structure). 비활성 검사기는 `disabled`(날짜·사유)에만. 루틴의 반복 고리 `run_gates.py check` 와 최종 기록
  `run_gates.py record` 가 이 목록만 돌린다. 지시문의 게이트 블록은 그 한 줄이다(`test_config.py` 가 강제).
- `record` 는 실제로 올릴 파일(노트까지 붙은 `posts/D.html`·`kr/posts/D.html`)에 목록을 돌리고, 프로그램이 직접
  모은 증거를 `verification/<market>/<D>.json` 에 쓴다: 글 sha256·blob, 검사기별 종료 코드·상태·시각·출력 해시·
  경고 수·위반 항목(경로 가림), 검사기 파일 해시, 입력 파일 해시(작업 공간), HEAD·미커밋 변경 해시, 파이썬 버전,
  기록 형식. 원시 출력은 공개 레포에 남기지 않는다.
- 글 바이트를 **한 번** 읽어 불변 사본(같은 파일 이름)으로 검사하고 그 바이트의 해시를 기록한다. 입력 해시와 레포 다이제스트
  (`scripts`·`config`·`research/<market>`, US 는 이 글을 뺀 `posts/` — 유동성 원장)를 검사 **전후**로 모아 다르면 차단한다.
  레포 다이제스트는 임시 index 에 `add -A` 해서 git 과 같은 방식으로 만든다 — 직접 해시하면 심볼릭 링크
  (`scripts/<p>/AGENTS.md`)가 git blob 과 달라 record → verify 가 영영 맴돈다(실제 검사기 모의 발행에서 나온 결함).
- 입력마다 같은 바이트가 이 커밋의 레포 경로에 있으면 `repo:<경로>` 로 참조(복원 가능), 없으면 `workspace-only`(해시만 —
  원본 보관은 다음 단계).
- 글과 기록은 **같은 커밋**. `verify --index`(커밋 직전), `verify --rev HEAD`(모든 push 직전 — rebase 뒤 포함)가 그 판의
  글·검사 코드·레포 다이제스트와 지금 입력이 기록과 짝인지 본다. record 와 **같은 입력 인자**(--tg·--stance-next)를 줘야 한다.
  어긋나면 record → add → `commit --amend`. 지시문은 verify 와 commit·push 를 `&&` 로 잇지 않는다(exit 4 에서 사슬이 멈춘다).
- 검사기별 exit 0 계약: `effective`(모듈의 적용일 — 그 전 글은 not_run), `indeterminate_patterns`(필수 입력이 없어 못 봄),
  `partial_patterns`(일부만 검사 — 막지 않되 검증 완료 아님), 기본 not_run 패턴(`nothing to check`·`검사하지 않는다`).
  `check_session` 은 볼 블록이 없을 때, `check_movers` 는 자료가 없을 때 그렇게 말하도록 출력만 바꿨다(종료 코드 그대로).
  자료 없이 움직인 종목 문단이 실렸으면 판정 불가(필수 → 보류) — 그 수치는 대조되지 않았다.

## 상태와 발행 여부(따로 낸다)

| 상황 | 기록 상태 | 발행 |
|---|---|---|
| 필수 검사 실패(노트를 빼도 남음) | fail | 보류 — 고쳐 다시, 최대 2회 |
| 필수 검사가 돌지 못함(예외·입력 오류·필수 입력 누락·시간 초과) | indeterminate | 보류(통과가 아니다) |
| 적용 대상이 아니라 건너뜀(적용일 전 등) | not_run | 막지 않음, 검증 완료 아님 |
| 경고만 | warn | 기존 규칙 |
| 참고 검사 실패 | fail | 막지 않음 |
| 노트 때문인 실패 — format | fail | 허용, `note_format` 에 기록 |
| 노트 때문인 실패 — numbers | fail | 허용하되 `note_numbers` — 검증 완료 아님 |
| 노트 때문인 실패 — structure(모르는 종류 포함) | fail | 보류 |
| 검사 중 원본 글·입력·레포 다이제스트가 바뀜 | integrity | 보류 — 다시 기록 |
| 레포 안 기록 저장 실패(4) | — | 같은 기록을 레포 밖(`fallback_record`)에 두고 `verify --record-file` 로 전부 대조, 발행 + 알림 「검증 기록 없음」(11/22 까지 시험 운영) |
| 기록 도구 오류·대체 기록도 실패(5) | — | **보류** — 최종 판이 검사됐다는 근거가 없다 |
| verify 가 git 을 못 읽음(2) | — | 보류(「기록 없음」과 다르다) |

노트 원인은 노트를 뺀 사본(같은 파일 이름·같은 입력)으로 다시 돌려 가르고, 실패 항목(정규화한 출력 줄)을 노트 구간·
본문으로 나눠 남긴다. 검사기 대부분이 구조화된 출력을 내지 않아 위치·종류를 줄에서만 읽으므로, 차단 여부는 항목
비교가 아니라 사본의 결과와 검사기 종류가 정한다. 노트는 AI 가 고치지 않는다. `close: on` 에서 최종 기록이 막히면
고쳐 쓰지 않고 pre 판(이 발행 건에서 게이트를 지난 판)으로 돌아가 **다시 기록해 통과해야만** 발행한다.

## 증명하지 않는 것

기록은 어느 바이트를 어느 검사기 버전이 어떤 입력으로 검사해 어떤 종료 코드를 냈는지를 남긴다. 검사기가 옳다는 것(회귀
시험 — 다음 단계), 데이터 출처가 옳다는 것, 수기 대조(문장 수치 표본 등)는 기록 밖이다. 기록은 루틴 샌드박스가 만든다 —
독립 확인은 다음 단계에서 알림 프로그램이 커밋된 blob 과 기록을 대조하는 것이다.
