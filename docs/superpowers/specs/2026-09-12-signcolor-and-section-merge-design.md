# 수치 방향색 · 스탠스/포트폴리오 병합 — 설계 (2026-09-12)

사용자 지시 5건. ① 「매크로 논리」→「매크로」, ② 수치를 경제·자산가격 기준 초록/빨강,
③ 주식 지수·섹터, ④ 채권은 **수익률 기준**(금리 하락=초록), ⑤ FX·원자재 「전일 대비」.
그리고 ⑥ 「멀티에셋 매니저 전략」과 「모의 포트폴리오」를 하나로 — "두 개가 중복되는 느낌".

## 색은 후처리다 — 작성 에이전트가 칠하지 않는다

칠할 칸이 하루 70개다(2026-09-10 발행본 실측). 사람이 손으로 칠하면 매일 틀리고,
게이트는 색의 «방향»을 검증할 수 없다. 그래서 `scripts/us/colorize.py` +
`scripts/apply_colors.py` 가 발행 직전에 결정론적으로 칠한다. 실행 위치는
`apply_readability.py` 다음, 나머지 게이트 앞.

`<td>` 에 `class="sc-up|sc-dn"` 만 얹는다. **새 요소를 만들지 않는다** — 텍스트 노드가
그대로라 수치 멀티셋 대조(`verify_post.py`), 분량 계측(`weight.prose_chars`), 문체·
매크로·포트폴리오 게이트가 전부 이 변경을 보지 못한다. 2026-09-12 codex 설계 검토가
여섯 파일(`portfolio_gate`·`macro_gate`·`check_weight`·`post_check`·`check_style`·
`readability`)을 대조해 반례 없음을 확인했다. 팔레트는 이미 쓰던 섹터 막대의
`#00A85A` / `#FF4040` 을 그대로 쓴다 — 한 문서에 두 가지 초록은 안 된다.

**class 이름은 `pos`·`neg` 를 쓰지 않는다.** 발행본마다 그 이름의 CSS 가 이미 있고
서식이 다르다 — 2026-08-18 은 `.pos{color}` 지만 2026-09-11 은 배경까지 깔린 배지다.
겹치면 칸에 초록 배경이 깔린다. 그리고 **우리 열이 아닌 칸은 속성도 건드리지 않는다** —
모든 칸의 class 를 다시 쓰던 첫 판이 옛 발행본의 손색 197개를 네 편에서 지웠다.

### 반전은 섹션 안에서만 걸린다

열 이름만 보고 문서 전체를 칠하면 「주간 변화」가 다른 섹션에 생긴 날 거꾸로 칠한다.
그래서 채권 섹션 안에서만 「전일 변화」·「주간 변화」를 반전하고, 매크로 섹션 안에서만
「최근」을 지표 극성으로 칠한다. 「전일 대비」·「등락」은 어느 섹션에서나 부호 그대로다.

`-0.00%` 는 무색이다. 부호만 보고 칠하면 움직이지 않은 날 빨강이 뜬다.

### 매크로는 판정을 다시 계산하지 않는다

**같은 행의 「판정」 칸이 정본이다** — `개선`·`악화`·`둔화`·`재가속`이 이미 계산돼 실려
있고, 그 어휘는 `macro_metrics` 가 극성을 반영해 만든 말이다(성장축 개선/악화, 물가축
재가속/둔화 → 좋은 쪽은 개선과 둔화). 첫 판은 `Actual` − `Previous` 부호에 지표별
극성을 곱해 다시 계산했는데, 그것이 §9 가 판정 어휘를 도입한 바로 그 사고다 —
2026-08-17 발행본은 실업수당이 **줄어든** 것을 원시 부호만 보고 「뚜렷하게 나쁜 방향」
이라 정반대로 서술했다. 게다가 판정은 모멘텀을 보므로 전기 대비와 어긋날 수 있어,
직접 계산하면 **같은 행에 인쇄된 판정과 색이 모순된다**.

판정 칸이 없는 옛 「최근 | 이전」 표에만 전기 대비 × 극성으로 대체한다. 그 극성은
`macro_metrics._POLARITY` 를 재사용하고, 축 정보는 `econ_indicators.json` 에만 있어
과거 발행본에 소급할 때 없으므로 물가 축 지표 이름 8개만 `colorize.INFLATION_AXIS` 에
둔다.

### 스탠스 섹션은 칠하지 않는다

멀티에셋 표의 「전일대비」는 가격 변화가 아니라 등급 이동(`유지`·`▲1단계`·`▼1단계`)이다.
부호로 읽으면 `▼1단계` 가 초록이 된다 — 2026-09-11 발행본에서 실제로 그렇게 나갔다.

### 훑는 것은 가린 사본에서, 고치는 것은 원문에서

주석 안의 가짜 `<h2>` 가 섹션을 끊어 채권 반전을 풀고, `<style>` 문자열 안의 가짜
`<tr>` 이 실제 칸처럼 고쳐졌다. 그래서 행과 제목은 `readability._blank_inert` +
`_MASKED_ELEMENT` 로 길이를 보존해 가린 사본에서 찾고, 수정은 원문의 같은 자리에
적용한다. 값은 칸 **맨 앞**의 한 수치만 읽는다 — 어디서든 첫 수치를 집으면
`<sup>1</sup>-0.32%` 의 각주 1 이 값을 이겨 손실 칸이 초록이 된다.

### 닫히면서 실패한다

`--check` 는 미적용이 있으면 **exit 1**. exit 0 으로 알리면 체인에서 이 단계가 빠진
날을 아무도 모른다. 마커는 **head 안 CSS 에서만** 인정한다 — 본문 주석 아무 곳의 같은
문자열로도 주입이 생략돼, class 만 있고 색 규칙이 없는 문서가 나갔다.

### 표만 칠한다 (한계)

산문 속 수치는 어느 지표에 속하는지 판정할 규칙이 없다. 잘못 칠한 색은 색이 없는 것보다
나쁘므로 칠하지 않는다. 문장-지표 귀속 규칙을 세우면 `colorize.paint()` 에 문단 경로를
더하면 된다. codex 는 이것을 「각 수치별」의 축소 해석이라 지적했고, 사용자에게 통보한
상태다.

## 병합 — 표 두 개를 합치지는 않는다

`<h2>멀티에셋 전략·포트폴리오</h2>` 하나에 스탠스 표와 포트폴리오가 함께 들어가고,
포트폴리오는 `<h3>모의 포트폴리오</h3>` 로 시작한다. **표 두 개를 물리적으로 합치지
않는다** — 행 축이 다르다(스탠스 7개 자산군 vs 슬리브 9개: 채권이 장기/단기로 갈리고
현금성이 추가된다). 억지로 합치면 빈 칸 표가 된다.

부모 제목에서 「모의」를 뺀 것은 stance 게이트가 찾는 필수 낱말이 「멀티에셋」뿐이고,
모의 운용 고지는 `data-portfolio="basis"` 문단에서 따로 강제되기 때문이다.

### 게이트 경계 — codex 설계 검토가 막은 다섯 구멍

1. **스탠스 셀도 h3 앞에서만 읽는다.** 텍스트만 자르고 `parse_stance_cells()` 에 구간
   전체를 넘기면, h3 뒤 표에 유효한 `data-asset` 을 숨겨 두고 위에는 표를 두지 않는
   경로가 열린다(등급 유지·축소일에는 트리거 인용도 필요 없다).
2. **병합 부모 h2 의 중복을 센다.** 숨은 사본이 검사를 통과하고 보이는 쪽이 창작을
   싣는 경로 — `stance_gate.heading_count()` 가 정확히 1회를 요구한다.
3. **stance locator 는 정확한 h2 제목만 본다.** 부분 문자열·본문 폴백을 쓰면 제목이
   틀린 섹션이 본문에 그 낱말이 있다는 이유로 통과한다. `weight.section_slice` 로 교체.
4. **포트폴리오 구간의 끝은 부모 구간의 끝이다.** 「다음 h3」에서 끊으면 h3 를 하나 더
   두어 그 뒤에 창작 수치를 park 할 수 있다.
5. **스탠스 분량 하한은 h3 앞만 센다.** 병합 섹션 전체로 재면 포트폴리오 산문이 하한
   1,800자를 대신 채워 준다. `measure()` 가 `stance_chars` 를 따로 계산해 담는다.

공용 `weight.section_slice()` 는 h2 전용으로 그대로 둔다 — h2|h3 로 바꾸면 매크로 가격
중복 검사가 h3 뒤를 놓친다. h3 는 `weight.sub_split()` 이 따로 다룬다.

### 2차 검토가 더 막은 것

6. **중복 계수와 구간 추출이 같은 정규화를 쓴다.** 추출은 엔티티를 디코드하는데 계수는
   안 해서, `멀티에셋 전략&#183;포트폴리오` 로 둘째 사본을 숨길 수 있었다.
7. **병합 섹션은 실제 `<section>` 안쪽만 본다**(`weight.section_scope`). `section_slice`
   는 다음 h2 까지 읽으므로 형제 `<aside>` 에 놓인 포트폴리오가 자식처럼 검사됐다.
   중첩 `<section>`(섹터 막대 스니펫)이 있으므로 깊이를 세어 짝을 찾는다.
8. **병합 제목이 있는 글에서는 옛 독립 h2 폴백을 허용하지 않는다.** 허용하면 새 구조
   글이 옛 구조로 발행되고도 통과한다.
9. **매크로 구간은 정확한 제목만 잡는다**(`locate_section(..., exact=True)`). 부분 문자열
   매칭은 은퇴한 「매크로 논리」 제목을 계속 통과시켰다.

## 소급 범위 — 검토 원장이 설명할 수 있는 만큼

소급의 한계는 「내가 봤는가」가 아니라 **`review/prose.py` 의 변환으로 옛 판을 밀어 새
판이 바이트 그대로 나오는가**다. 나오지 않는 소급은 그만큼을 codex 미검토 큐로 쏟아
넣는다 — 첫 판이 큐를 3건에서 44건으로 불렸다.

- **색은 `posts/*.html` 전체(42편)에 소급한다.** 색칠은 도구가 매 발행마다 내는
  변환이므로, `known_blocks` 에 「조판 + 색」 블록을 등록하고 `prose.transformed()`
  체인에 `paint()` 를 더하면 `refresh` 가 조판으로 접는다. 손으로 넣은 기존 색은
  그대로 남는다(우리 열이 아닌 칸은 건드리지 않는다).
- **제목 「매크로」는 소급하지 않는다.** 한 번만 하는 텍스트 변경은 어떤 변환으로도
  설명되지 않는다. 옛 글에는 당시 이름이 사실이므로 코드·문서·앞으로의 발행분만
  바꾼다. 첫 판에서 19편에 소급했다가 되돌렸다.
- **병합도 소급하지 않는다.** 구조를 바꾸면 `post_check` 의 태그 시퀀스 대조가
  어긋나고 리딩맵 앵커가 죽는다. 게이트는 새 구조만 통과시키면 된다.
- 그래서 `test_weight` 의 실물 발행본 테스트는 **제목 둘을 테스트 안에서** 새 계약으로
  옮겨 붙여 계측 코드를 잰다.

### 변환이 둘 겹치면 각각으로는 설명되지 않는다

임베드 이미지가 남아 있던 옛 판 28편은 색만 더해도 막혔다 — `asset_externalized` 가
「src 밖 바이트가 다르다」며 False 를 줬고, `equivalent` 는 그림이 달라 False 였다.
그래서 `typography()` 에 **조합 경로**를 넣었다: 조판·색을 먼저 입히고 나서 자산
외부화만 남는지 본다. 방향은 그대로 — 되감아 바이트가 같은지만 본다. 색은 값에서
결정론적으로 다시 계산되므로, **손으로 바꿔 넣은 색은 이 변환을 통과하지 못한다.**
